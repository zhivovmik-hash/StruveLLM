# Struve LLM

Сначала проверь `Get-Command struve-llm`. Если текущий процесс ещё не получил обновлённый PATH, используй `.\bin\struve-llm.cmd`. Выполни `--json doctor`; он запускает постоянный локальный диспетчер при необходимости. `--no-start` оставляет запуск под контролем вызывающей стороны.

Выполняй команды относительно распакованной папки. При переносе не предполагай те же диски: прочитай `doctor`, `resources list`, `settings get`. README установленного исходного кода содержит форматы объектов и границы версии. GUI и CLI разделяют SQLite-базу; не изменяй её напрямую.

Сначала открой `project list`, `profile list`, `mcp list` или `plugin list`. Повторно используй `id`. Для изменения получи актуальный объект и сохрани поле `revision`; конфликт означает необходимость перечитать состояние. Перед установкой пакета используй `plugin install --dry-run`. Raw-команда `request` предназначена только для чтения и проверки.

```powershell
struve-llm --json resources list
struve-llm --json resources plan --profiles cpu-diagnostics
struve-llm --json mcp probe local-diagnostics
struve-llm --json mcp call local-diagnostics --tool runtime_info --project struve
```

Секреты настраиваются через окно или `secret set --name NAME` с вводом значения через stdin. В конфигурации MCP сохраняются только имена. Не печатай токены, не включай их в аргументы команд, логи или манифесты.

`mcp probe` устанавливает связь и получает метаданные; вызов инструмента — отдельная операция. Перед вызовом учитывай его реальный эффект и поручение пользователя. Плагины не расширяют полномочия поручения. Наличие readOnlyHint у внешнего сервера не является доказательством безопасности.

## Модели и локальные поручения

Версия 0.3 имеет управляемые движки Ollama и произвольную программу локального API с массивом аргументов без shell. Сначала прочитай `model list`, `model get ID` и связанный профиль. `model start ID` запускает движок, `model stop ID` завершает его и зависимые активные задачи. Настройку работающего движка сначала останови; не прерывай чужую конвертацию или задачу ради обновления. Внешний уже работающий API приложение не ограничивает.

```powershell
struve-llm --json model list
struve-llm --json attachment add "C:\Project\report.md"
struve-llm --json chat send --file task.json
struve-llm --json run get TASK_ID
struve-llm --json run wait TASK_ID
struve-llm --json run cancel TASK_ID
struve-llm --json chat get CHAT_ID
```

`task.json` содержит `project_id`, `model_id`, `content`, необязательные `chat_id`, `attachment_ids`, `use_tools`, `tool_selection` и `max_tool_calls`. Пример выбора: `"tool_selection":[{"connection_id":"documents","tool":"document_read"}]`. Получай имена из актуального каталога подключений. Без `tool_selection` CLI передаёт все разрешённые проекту инструменты; пустой массив не передаёт ни одного. Выбирай минимальный набор для конкретного поручения. Лимит задаётся моделью: по умолчанию 4, допустимо 0–8. Поручение может его уменьшить, но не увеличить. Ноль отключает инструменты.

Формулируй ограниченную задачу, входные файлы, требуемый результат и критерии проверки. Проверяй сохранённый `run`, реальные квитанции инструментов и факты результата; текст модели не доказывает, что действие произошло. Сначала используй локального агента для чтения журналов, кратких сводок и подготовки предложений. Возврат `completed` означает техническое завершение, а не научную приёмку.

`chat send --wait` и `run wait` дают ненулевой exit code при failed/cancelled/interrupted; JSON сохраняет терминальную запись в `data` и код `TASK_FAILED`. `run get` — обычный запрос состояния. После отмены частичный ответ остаётся в задаче и в истории чата с пометкой отмены; в контекст следующего запроса он не передаётся. Не дублируй незавершённое поручение; сначала прочитай его статус. Закрытие окна сохраняет диспетчер, перезапуск диспетчера прерывает его процессы и отмечает незавершённые задачи.

Контекст имеет явный предел. Документы могут быть обрезаны с предупреждением; проверяй его. Видео представлено четырьмя кадрами без аудио. Для модели с кастомным шаблоном доступен `tool_mode: json`; качество проверяй на конкретной установленной модели. Не считай заявленное окно контекста, поддержку инструментов или vision автоматически проверенными.

## Ресурсы и полномочия

`instance start --file spec.json --dry-run` проверяет общий launcher. RAM и доля CPU ограничиваются Windows Job Object для дерева процессов; VRAM проверяется при допуске, аппаратной квоты VRAM нет. GPU выбираются по актуальным UUID, отсутствующие устройства не подменяются другими. Профили с устаревшим железом могут сохраняться, но не проходят запуск. Изменение профиля применяется к следующему запуску; работающий процесс сохраняет снимок профиля. В media-модели `offload_to_cpu` хранит веса в RAM, а `diffusion_cpu` переносит сами diffusion-вычисления на CPU/RAM; это разные режимы. `text_encoder_cpu` и `vae_cpu` независимы. Проверяйте фактические аргументы и журнал, не обещайте, что RAM автоматически заменит CUDA-буферы.

`instance stop ID` отменяет связанную задачу агента; для экземпляра движка также отменяет все его активные задачи. В окне активные процессы отделены от истории. `snapshot` и журнал окна возвращают последние 100 событий; полная история читается командой `events` по курсору.

`resources plan` проверяет наличие ресурсов. Научные обучения, подбор гиперпараметров, продвижение checkpoint и изменение рабочих научных данных требуют соответствующего поручения пользователя. Очередь медиагенерации обслуживает создание и редактирование изображений и видео.

`mcp serve` экспортирует координатору восемь инструментов чтения и планирования. Для записи используй именованные CLI-команды. CLI stdout с `--json` содержит один объект, не извлекай статус из текстовых логов. События читаются через `events --after CURSOR --limit 100`.

## Настройки моделей 0.4

`model get` / `model save --file` поддерживают параметры генерации, `system_prompt`, массив `skills`, `max_tool_calls`, `agent_timeout_seconds` (1–1200), `max_attachment_files` (0–8) и `tool_allowlist`. Пустой `tool_allowlist` запрещает все инструменты; null наследует разрешения проекта. Навыки являются инструкциями, не разрешением на инструменты или обучение. Скрипты из пакетов навыков не исполняются автоматически.

`model skill-import ID --file SKILL.md --disabled` добавляет снимок текста к модели. Для включения/изменения навыка сохрани актуальный объект модели с revision. `model plan --file model.json` проверяет аппаратную привязку без сохранения или запуска. Для индивидуальных ресурсов передай `resource_profile` с GPU UUID, бюджетами RAM/VRAM/CPU и revision существующего индивидуального профиля. Сервер атомарно сохранит профиль и модель. Не меняй привязку работающего движка без его штатной остановки; не прерывай пользовательские задачи ради настройки.

`run get` → `execution` сохраняет снимок модели, профиля и ограничений данного поручения. Диспетчер дополнительно контролирует разрешённые инструменты, число вызовов и дедлайн. Температура/Top P/seed и другие значения должны подтверждаться фактическим запросом/результатом, а не только наличием полей в конфигурации. Полная инструкция: `docs/MODEL_SETTINGS_040_RU.md`.

## Изображения и видео 0.7

Медиа-модели имеют отдельный каталог и независимые профили. Сначала прочитай `media list`, `media defaults`, `media get ID`, `resources list` и активные `run list`. Семейства: SD 1.5, SDXL, SD 3.5, FLUX.1, FLUX.2 Klein, MiniMax H3. Наличие шаблона не означает установку весов или проверку GPU.

Для H3 `sampling_schedule` отсутствует/`standard` у обычных весов либо равен `hyperflow-h3-flash-4`, `hyperflow-h3-flash-6`, `hyperflow-h3-flash-8` у отдельных весов HyperFlow H3 Flash. В последнем случае `steps` обязан совпадать, `sampling_method` — `euler`, `cfg_scale` — 1. Параметр передаётся как `--sigmas`; это не флажок Flash Attention. `vram_gib` передаётся sd.cpp как `--max-vram` для бюджета размещения весов, без обещания жёсткой квоты или автоматического переноса CUDA-буферов в RAM.

`media save --file model.json` атомарно сохраняет модель и её `resource_profile`; сохраняй актуальные revision обоих объектов. `media check --file` проверяет файлы и допуск ресурсов, но не CUDA и не качество генерации. Не меняй профиль медиа-модели через `profile save`. `media defaults --file` задаёт роли image/edit/video. Во время активного медиацикла настройки защищены; не прерывай чужую задачу ради изменения параметров.

В `chat send` передавай `mode` (`auto`, `text`, `image`, `edit`, `video`) и при необходимости `media_model_id`. Языковая `model_id` планирует запрос. Генератор выбирается отдельно. Для правки используй существующий `chat_id` с настоящим изображением либо одно импортированное изображение в `attachment_ids`. Для продолжения видео в том же чате передай «Продли до 7 секунд». Допустимая общая длительность составляет 1–15 секунд. Исходный файл сохраняется.

Для H3 FL2VA можно передать ровно два изображения в `attachment_ids`: первое задаёт начальный кадр, второе — конечный. В сценарии явно задай действия и ограничения; проверь `video_reference_end` и фактические `--init-img` / `--end-img`. Это не произвольный набор референсов Ref2VA. Сценарий и техническая передача референсов не доказывают, что модель правильно воспроизвела движение: просматривай готовое видео.

Проверяй `run.artifacts`, фактический файл, визуальное содержание, `llm_restored` и отсутствие активных рабочих процессов этого run. Для изображений проверь маску и `edit_metrics`: ноль изменений вне маски не доказывает правильную правку внутри неё. Для видео проверь число декодируемых кадров и переход между исходником и продолжением. H3 использует собственное число кадров 5 + 17 × N при 24 fps; заданная в запросе длительность обрезается до целевого числа кадров без изменения настройки модели. Не подменяй неудачную локальную генерацию облачным результатом.

Для H3 в движке Struve RAM поле `h3_linear_chunk_tokens` задаёт порцию линейных вычислений в токенах. Пустое значение наследует настройку движка. Допустимы целые числа от 0 до 65536, ноль снимает ограничение. Проверь фактическую передачу `--model-args minimax_h3_linear_chunk_tokens=N` и журнал движка.

Во время рендера H3 читай `run get TASK_ID`. Поле `render_progress.stage` показывает `conditioning`, `diffusion`, `vae_decode` или `writing_video` по сообщениям движка. `steps_completed` и `steps_total` внутри `render_progress` относятся к диффузии. Пока поле отсутствует, ориентируйся на `phase` и журнал процесса. Для готового результата проверь `status=completed` и файл в `artifacts`.

При занятой карте медиа-поручение может вернуться со статусом `queued` и этапом `waiting_for_gpu`. Используй ID из этого ответа. Диспетчер сам передаст задаче ресурсы, когда освободится карта и планировщик. `run wait ID` ждёт до конечного состояния, `run cancel ID` снимает ожидающее поручение. Ожидание сохраняется при перезапуске диспетчера. Поручение, которое в момент перезапуска уже исполнялось, получает статус `interrupted`.

Для готового ролика с неподвижной камерой `media level-exposure RUN_ID` создаёт отдельное вложение на CPU. Параметр `--profile PROFILE_ID` выбирает профиль без GPU. Проверь `attachment.path`, `source_attachment_id` и оба SHA-256 в `metrics`. Копия доступна в исходном сообщении и в `run.exposure_copy`. Повторный вызов возвращает ранее проверенную копию.

## Ресурсы и память в 0.8

Используйте `resources history --model ID` для измерений и `resources estimate ID --context 4096` для сопоставимых запусков. В ожидающей задаче читайте `run get ID` и поле `wait_reason`. Суммарные лимиты проверяются командой `resources plan --profiles PROFILE_A,PROFILE_B`. Для файлового источника внутри проекта доступны `memory index`, `memory find-source`, `memory source` и `memory refresh`. Команда `memory semantic --project PROJECT build` создаёт дополнительный локальный индекс на CPU.
